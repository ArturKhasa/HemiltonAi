## C1. Статус не переключается автоматически

**Проблема.** Менеджер открывает список и видит одинаковый «Поинтересовался» и у
того, кто написал «привет» минуту назад, и у того, кто получил расчёт, назвал
город и размер. Отобрать «кому отправлен расчёт» невозможно — фильтр по статусу
показывает 89 диалогов из 834 реальных.

**Причина. Статус в системе умеет менять ровно один участник — модель**, полем
`next_status` ([app/ai/schemas.py:7](../app/ai/schemas.py#L7), применяется в
[app/ai/runner.py:1695](../app/ai/runner.py#L1695)). Отсюда две независимые
дыры:

1. **Половину пути клиент проходит вообще без модели.** Приветствие уходит
   скриптом дословно, без обращения к модели
   ([`_run_scripted_greeting`, runner.py:2070](../app/ai/runner.py#L2070)), а
   следом за ним связка `follow_up_script_id` разворачивает «2. Похвала → 2.2
   Стоимость → 2.3 Доставка» — то есть **расчёт клиенту отправляет связка
   скриптов**. Молчуну цену досылает
   [app/ping/silent_greeting.py:101](../app/ping/silent_greeting.py#L101).
   Дальше работают пинги. Ни один из этих трёх путей к статусу не прикасается:
   `funnel_stage` они выставляют, статус — нет. Это те самые 218 диалогов.
2. **Когда модель работает, она молчит про статус в 55 % ходов.** Промпт просит
   выбирать статус после каждого ответа
   ([app/ai/prompts.py:12](../app/ai/prompts.py#L12)), но `next_status` — поле
   необязательное, и «оставить как есть» для модели всегда безопаснее. Отсюда
   45 диалогов, где SalesAgent отработал 4+ раза, а статус не сдвинулся.

Дополнительно мешает **устаревшее описание статуса**: «Горячий» в базе описан
как «запрашиваем фото объекта/замеров» — текст приехал из миграции
[012](../app/db/migrations/versions/012_dialog_statuses.py#L36), написанной под
другой бизнес. Модель выбирает статус по этому описанию.

**Как исправляем. Статус считает код по фактам, а не модель по ощущению.**

Новый модуль `app/sales/status_flow.py` с одной функцией
`sync_status(db, dialog)`, которая поднимает диалог по лестнице до самой дальней
ступени, факт которой подтверждён. Все детекторы уже написаны и обкатаны —
новой эвристики не изобретаем:

| Ступень | Факт, по которому ставится | Чем проверяем |
|---------|---------------------------|---------------|
| Поинтересовался | диалог заведён | стартовый статус вебхука ([vk/webhook.py:285](../app/vk/webhook.py#L285)) |
| Есть расчёт | сумма **дошла** до клиента | `dialog.quoted_prices` + `_prices_in(delivered_outgoing_texts())` — связка из [runner.py:928](../app/ai/runner.py#L928) |
| Уточняем детали | клиент ответил после расчёта | `collect_slots()` дал город/цвет/размер ([order_slots.py:201](../app/sales/order_slots.py#L201)) |
| Горячий | отправлены способы оплаты | `CHECKOUT_PRESENTED_RE` ([funnel_steps.py:531](../app/sales/funnel_steps.py#L531)) |
| Ждём данные | запрошены ФИО и телефон | скрипт «5.1 Данные перед оформлением» ([funnel_steps.py:537](../app/sales/funnel_steps.py#L537)) |
| Ждём предоплату | ссылка/реквизиты ушли | `dialog_has_payment_link()` ([funnel_steps.py:821](../app/sales/funnel_steps.py#L821)) |
| Заказ оформлен | оплата подтверждена | `dialog.payment_confirmed_at` |

Три правила, без которых лестница вредна:

- **Только вперёд.** Ступень ниже текущей не ставится никогда — иначе диалог
  поедет назад, как это уже было («Горячий» → «Есть расчет» → «Горячий», диалог
  142, см. [status_names.py](../app/sales/status_names.py)).
- **Боковые статусы неприкосновенны.** «Нужен куратор», «Спам», «ЧС» ставят свои
  ветки (триггеры, эскалация пинга, отписка), лестница их не перетирает и из них
  не выводит.
- **Считаем по доставленному.** Источник — `delivered_outgoing_texts()`, то есть
  сообщения, которые ВК/MAX действительно принял. Отметка в базе не годится:
  на этом уже обжигались (диалог 78880, 24.08 — цена закреплена, а сообщение не
  доехало).

Важный побочный эффект: `delivered_outgoing_texts()` читает и сообщения
менеджера. Значит статусы начнут считаться и у 665 диалогов, которые ведёт живой
оператор при выключённом ИИ, — но только там, где менеджер отправил узнаваемый
текст скрипта (сумма, способы оплаты, ссылка). Свободный пересказ менеджера
регулярка не увидит; распознавать его — отдельная задача с классификатором, и
без запроса ОП я её не делаю.

**Точки вызова** — по одной на каждый путь, которым сообщение уходит клиенту:

1. `run_ai` — сразу после гейтов ([runner.py:1695](../app/ai/runner.py#L1695));
2. `_run_scripted_greeting` — после связки со стоимостью;
3. `silent_greeting._send_price` — догоняющая цена молчуну;
4. `ping/worker._process_state` — после отправки пинга;
5. ответ менеджера из панели ([app/api/chat.py](../app/api/chat.py)).

**Роль модели сужается до боковых статусов.** `next_status` остаётся, но из
списка в промпте (`format_statuses_block`,
[prompts.py:7](../app/ai/prompts.py#L7)) убираем ступени лестницы: модель
предлагает только «Нужен куратор», «Спам», «ЧС». Так исчезает и разнобой 45 %,
и лишний повод для галлюцинации.

**Гейты в `status_names.py` переписываем под новую лестницу:** из «Горячего»
дорога теперь в «Ждём данные» и «Ждём предоплату», а «Ждём предоплату»
разрешено ставить и из «Уточняем детали» / «Ждём данные». Сейчас там ровно два
имени, и любой новый статус их сломает.

**Пересчёт прошлого** — отдельная команда `python -m app.commands.resync_statuses
[--days N]`: гоняет ту же `sync_status` по существующим диалогам. Запускаем
руками, не миграцией: 79 тысяч строк лучше трогать осознанно и с ограничением по
дате (вопрос 3).

## C2. Статусов из нового списка нет в базе, описания старых устарели

**Проблема.** В присланном списке десять статусов, в базе — девять, и это не те
же девять:

| В базе (прод) | В списке ОП |
|---------------|-------------|
| Поинтересовался | ✅ |
| Есть расчет | ✅ (в списке — «Есть расчёт», через «ё») |
| — | **Уточняем детали (новый)** |
| Горячий | ✅, но **смысл другой** |
| — | **Ждем данные** |
| Ждем предоплату | ✅ |
| Заказ оформлен | ✅ |
| Нужен куратор | ✅ |
| Спам | ✅ |
| ЧС | ✅ |
| Горячий клиент | мёртвый дубль: 0 диалогов, пустое описание |

Смысл «Горячего» меняется: было «клиент подтвердил интерес после расчёта»,
стало «отправили клиенту способы оплаты заказа» — это на две ступени дальше.

**Причина.** Статусы — строки в таблице `dialog_statuses`, их заводят руками в
админке, а код узнаёт их по имени
([app/sales/status_names.py](../app/sales/status_names.py)). Дубль «Горячий
клиент» (id 9) появился именно так и уже один раз положил все три гейта воронки.

**Как исправляем.** Миграция `054_status_ladder`, чтобы прод и dev не разъезжались:

1. добавить «Уточняем детали» и «Ждем данные» (если их ещё нет);
2. переписать `pattern` всем ступеням текстами из письма ОП — включая «Горячий»,
   где сейчас лежит описание из чужого бизнеса;
3. погасить дубль «Горячий клиент» (`is_active = false`), диалогов на нём нет;
4. те же имена — в `DEFAULT_STATUSES` сидера
   ([app/commands/seed.py](../app/commands/seed.py)).

Порядок статусов в панели — по `id`, поэтому новые встанут в конец списка. Чтобы
селект в шапке диалога читался лестницей, добавляю в таблицу колонку
`sort_order` и сортирую по ней (10 минут, иначе «Уточняем детали» будет висеть
после «ЧС»).

Цвета бейджей для двух новых статусов — в `STATUS_COLORS`
([ChatPage.vue:1385](../frontend/src/pages/ChatPage.vue#L1385)): «Уточняем
детали» — бирюзовый, «Ждем данные» — янтарный, между фиолетовым «Есть расчет» и
красным «Горячий».

## C3. Не видно, по каким диалогам идут пинги

**Проблема.** Пингуется диалог или заброшен — понятно только изнутри: полоска
воронки нарисована в шапке открытого диалога
([ChatPage.vue:227](../frontend/src/pages/ChatPage.vue#L227)). Чтобы понять, надо
ли брать лид руками, менеджер открывает каждый.

**Причина.** В списке этих данных просто нет: `DialogListItem`
([chat.py:65](../app/api/chat.py#L65)) отдаёт статус, стадию, метку и паузу —
про `dialog_ping_states` не знает ничего. Фильтр `ping_funnel_type` в API есть,
но воронка в базе одна (`knows_price`), и фильтр по ней ничего не разделяет:
он не отличает активную воронку от завершённой.

**Как исправляем.**

1. **Признак в API.** Поле `ping_active: bool` в `DialogListItem` —
   `EXISTS (select 1 from dialog_ping_states where dialog_id = … and is_completed = false)`.
   Рядом `ping_next_at` — время следующего пинга, в подсказку бейджа. Это
   честный признак: диалог, чья воронка закрыта, новую уже не получит —
   `discover()` пропускает всех, у кого запись есть
   ([worker.py:796](../app/ping/worker.py#L796)).
2. **Бейдж в строке списка** — в тот же ряд, где провайдер, статус и метка.
   Красный, как просил ОП, но **заливкой** (`bg-red-500 text-white`), а не
   пастелью: пастельно-красный уже занят статусом «Горячий», и рядом они
   читались бы как два статуса. Подпись «● ИДЁТ ПИНГ», в `title` — «Следующий
   пинг: 27.08 16:56».
3. **Бейдж гаснет, когда пингов не будет.** Воркер закрывает воронку, если ИИ на
   паузе, клиент ответил или отправка заблокирована
   ([worker.py:367-425](../app/ping/worker.py#L367)) — но узнаёт об этом только
   на своём ближайшем проходе, а до него `is_completed` ещё `false`. Поэтому в
   выдаче прячем бейдж при `ai_paused` и `vk_blocked` — тех же условиях, по
   которым воронку закроет воркер. Иначе красная метка обещала бы пинг, которого
   не будет.
4. **Фильтр «Идёт пинг»** в модалке фильтров — галочка. Ложится в общую
   `_apply_dialog_filters` ([chat.py:85](../app/api/chat.py#L85)), поэтому сразу
   работает и в списке, и в счётчике «Найдено», и в обеих выгрузках.
5. **Колонка `ping_active`** в CSV — одна строка, ОП считает по выгрузке.

Сейчас под бейдж попадают 168 диалогов из 583 заведённых воронок.

## C4. Не видно, из какого мессенджера клиент

**Проблема.** ВК и MAX в списке неотличимы. При этом ведут они себя по-разному:
в MAX клиент получает приветствие и цену, не написав ни строчки, менеджер
отвечает мимо панели, а «ID клиента» — не VK ID.

**Причина.** Платформа лежит на канале (`vk_groups.platform`,
[models.py:91](../app/db/models.py#L91)) и доезжает только до карточки открытого
диалога — `GET /dialogs/{id}` ([dialogs.py:126](../app/api/dialogs.py#L126)),
где ею подписаны «MAX ID» и «MAX не принимает отправку». В списке
(`list_chat_dialogs`, [chat.py:293](../app/api/chat.py#L293)) `VkGroup` не
джойнится вовсе.

**Как исправляем.**

1. `outerjoin(VkGroup, Client.vk_group_id == VkGroup.id)` в запросе списка —
   `Client` там уже есть, лишнего запроса не появится. Поле `platform` в
   `DialogListItem`, `'vk'` по умолчанию (тестовый диалог из панели канала не
   имеет).
2. Бейдж «ВК» / «MAX» в строке списка: ВК — синий (`bg-sky-100 text-sky-700`),
   MAX — фиолетовый (`bg-violet-100 text-violet-700`).
3. Фильтр «Платформа» (ВК / MAX) — в ту же общую функцию фильтров.
4. Колонка `platform` в выгрузке CSV.

Объём на сегодня: 428 диалогов MAX против 79 446 ВК за две недели — то есть
MAX-лид в общем списке сейчас теряется полностью.

## Вопросы заказчику

1. **«Уточняем детали (новый)» — как статус должен называться в панели?**
   Беру «Уточняем детали», слово «(новый)» считаю пометкой для меня, а не частью
   имени.
2. **«Горячий» меняет смысл** — было «подтвердил интерес после расчёта», стало
   «отправлены способы оплаты». Сейчас на нём висят 174 диалога по старому
   смыслу. Оставить как есть (новые будут считаться по-новому) или пересчитать
   все и часть откатить в «Уточняем детали»?
3. **Пересчитывать ли статусы задним числом?** Могу прогнать лестницу по всей
   базе (79 тыс. диалогов) или только по свежим — предлагаю за последние 30
   дней, старое не трогать.
4. **Что делать, если менеджер поставил статус руками?** Предлагаю: автоматика
   двигает только вперёд и никогда не откатывает, но и не замирает. Если нужно,
   чтобы ручной статус замораживал диалог совсем — это отдельная колонка и
   +2 часа.
5. **«Есть расчёт» или «Есть расчет»?** В базе статус без «ё». Переименовать
   ради буквы можно, но имя статуса — то, по чему его находит код, так что
   лучше решить один раз.
6. **Тег «Идёт пинг» — заливкой алым (белый текст) вместо пастели?** Пастельно
   красный уже занят статусом «Горячий», рядом они сольются.
7. **Показывать ли тег, когда ИИ на паузе?** Формально воронка ещё не закрыта,
   фактически пинга не будет — предлагаю не показывать.

Ответы нужны на 1, 2 и 3; остальное сделаю по предложенному варианту, поменять

## Что сделано

### C1. Ступени воронки считает код

Новый модуль [app/sales/status_flow.py](../app/sales/status_flow.py):
`earned_status()` возвращает самую дальнюю ступень, факт которой подтверждён
**доставленным** сообщением, `sync_status()` поднимает на неё диалог. Только
вперёд; боковые статусы («Нужен куратор», «Спам», «ЧС») не трогает и из них не
выводит; нет статуса в базе — молча ничего не делает, ход не падает.

Вызывается из пяти мест — по одному на каждый путь, которым текст уходит клиенту:

| Где | Что закрывает |
|-----|---------------|
| [vk/webhook.py `deliver_parts`](../app/vk/webhook.py) | ответ ИИ, скриптовое приветствие и связка со стоимостью — обе платформы |
| [ping/silent_greeting.py](../app/ping/silent_greeting.py) | догоняющая цена молчуну |
| [api/chat.py `reply_as_manager`](../app/api/chat.py) | ответ менеджера из панели |
| [vk/webhook.py `handle_message_reply`](../app/vk/webhook.py) | менеджер забрал диалог из интерфейса ВК |
| [max/manager_watch.py](../app/max/manager_watch.py) | менеджер ответил в MAX мимо панели |

Плюс тестовый диалог в панели — там отправки в мессенджер нет, лестница
двигается сразу, иначе воронку негде проверить.

Ступень ставится по факту доставки, а не по факту записи в базу: диалог 78880
(24.08) — связка с ценой не доехала, а сумму за диалогом уже закрепили.

**Роль модели сужена до боковых статусов.** `next_status` со ступенью воронки
игнорируется с записью в лог; в промпт ([prompts.py](../app/ai/prompts.py))
уходят только «Нужен куратор», «Спам», «ЧС». Три гейта в runner, каждый из
которых чинил свой случай выдуманного статуса (откат из «горячего», предоплата
на первом сообщении, предоплата без ссылки), удалены: они лечили корень, которого
больше нет.

`_MONEY_RE` / `_prices_in` вынесены из runner в
[app/sales/prices.py](../app/sales/prices.py) — лестница задаёт тот же вопрос
«клиент уже видел сумму?», а тянуть ради него весь runner не может.

### C1a. Рассылки — находка, изменившая решение

Первый же замер лестницы на боевой базе дал 78 065 диалогов, которые уехали бы в
«Есть расчет». Причина: **массовые рассылки лежат в тех же строках с ролью
`curator`** — 637 807 сообщений из 667 561, — и цена в них обычное дело.
«💥ТОЛСТОВКА ЗА 4 990₽ + 3 ПОДАРКА» ушла в 58 238 диалогов, «300 руб. — и скидка
25 %» — в 73 716. Расчётом считался бы каждый, кому пришло рекламное письмо.

Два правила против этого:

1. **Пометка рассылки в базе.** Вебхук уже опознаёт рассылку по разлёту
   ([app/vk/broadcast.py](../app/vk/broadcast.py)), но держал это только в памяти
   процесса. Теперь пишет в метаданные сообщения `broadcast: true`, и лестница
   такие сообщения не читает. На историю пометку расставляет новая команда
   `python -m app.commands.mark_broadcasts` (637 812 сообщений).
2. **Реплики менеджера засчитываются только там, где клиент заговорил.** Пометка
   ловит не всё: у персонализированной рассылки имя стоит и в середине
   («⏰ Андрей, осталась всего неделя… Один свитшот — 4 790 руб.»), порога по
   разлёту она не набирает и от менеджерской реплики по тексту не отличается.
   Зато отличается диалогом: у диалога 383 двенадцать рекламных писем и ни одного
   сообщения клиента — отвечать там некому. Наши собственные сообщения (роль
   `ai`) засчитываются всегда: в MAX клиент получает приветствие и цену, не
   написав ни строчки.

После обоих правил замер выглядит так (14 дней, `is_test = false`):

| Сейчас | Станет | Диалогов |
|--------|--------|---------:|
| Поинтересовался | Поинтересовался | 78 087 |
| Поинтересовался | Есть расчёт / Уточняем детали | 1 041 |
| Поинтересовался | Ждём предоплату | 179 |
| Поинтересовался | Горячий | 63 |
| Поинтересовался | Ждём данные | 28 |
| Горячий | Есть расчёт / Уточняем детали | 76 |
| Горячий | Ждём предоплату | 26 |
| Есть расчет | Горячий | 10 |

78 тысяч, оставшихся на первой ступени, — это получатели рассылок, которые нам не
написали ни слова: из 79 397 диалогов в «Поинтересовался» сообщение клиента есть
у 2 625. Двигаются ровно те, где разговор был.

### C2. Статусы в базе

Миграция [054_status_ladder](../app/db/migrations/versions/054_status_ladder.py):
добавлены «Уточняем детали» и «Ждем данные», всем десяти статусам переписаны
описания текстами ОП (у «Горячего» лежало «запрашиваем фото объекта/замеров» из
миграции 012 — от другого бизнеса), пустой дубль «Горячий клиент» погашен.
Колонка `sort_order` расставляет статусы лестницей: по `id` новые встали бы после
«ЧС». Проверено на живом Postgres, включая откат и повторный накат.

Цвета новых бейджей в панели: «Уточняем детали» — бирюзовый, «Ждем данные» —
янтарный, между фиолетовым «Есть расчет» и красным «Горячий».

### C3. Тег «ИДЁТ ПИНГ»

Поля `ping_active` и `ping_next_at` в списке диалогов, красный бейдж **заливкой**
(пастельно-красный занят статусом «Горячий»), в подсказке — время следующего
пинга. Фильтр «Пинги: идёт / нет» и колонка `ping_active` в выгрузке CSV.

Метка гаснет там, где пинга не будет: воронка закрыта, воронки нет вовсе, ИИ на
паузе, отправка заблокирована. Последние два — те же условия, по которым воронку
закроет воркер, но узнает он об этом только на ближайшем проходе.

Побочно: лестница не заводит воронку `after_payment`, если диалог уже ведёт
человек. Иначе счёт, выставленный менеджером, тут же перезапускал бы пинги
поверх живого разговора.

### C4. Платформа

Поле `platform` в списке диалогов (через `outerjoin` на канал клиента), бейджи
«ВК» (синий) и «MAX» (фиолетовый), фильтр «Платформа» и колонка в CSV. Диалог без
канала — тестовый из панели — считается ВК, как и везде в коде.

### Пересчёт истории

Порядок запуска на проде **после** выката:

```
python -m app.commands.mark_broadcasts       # ~638 тыс. сообщений, один раз
python -m app.commands.resync_statuses --dry-run
python -m app.commands.resync_statuses       # вся база, откат разрешён (ответ 2)
```

У обеих команд есть `--dry-run`; у пересчёта — `--days N` и `--forward-only`.
Боковые статусы не трогаются ни при каких флагах.
